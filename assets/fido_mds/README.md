# FIDO MDS signing trust

`root-r46.pem` is the self-signed GlobalSign Root R46 certificate designated by the
[FIDO Alliance metadata page](https://fidoalliance.org/metadata/) as the MDS BLOB signing
trust anchor. It was retrieved on 2026-10-12 from
[GlobalSign's certificate distribution](https://secure.globalsign.com/cacert/rootr46.crt).
The published PEM is also available on
[GlobalSign's root test page](https://valid.r46.roots.globalsign.com/).

SHA-256 over its DER encoding:
`4FA3126D8D3A11D1C4855A4F807CBAD6CF919D3A5A88B03BEA2C6372D93C40C9`.

The public CA root is insufficient by itself: the signing leaf must have the exact SAN
`mds.fidoalliance.org`, digital-signature usage, TLS server-authentication usage, and valid
non-CA constraints. The current official service uses RS256 with an `x5c` signing chain.
Unknown JWS headers, alternative algorithms, and header-directed certificate downloads are
rejected. Supporting a future signing profile or trust-root rotation requires a reviewed
code/asset update; trust anchors are never accepted from the downloaded BLOB.

Following the [MDS processing rules](https://fidoalliance.org/specs/mds/fido-metadata-service-v3.1-ps-20250521.html),
all non-root signing-chain certificates require fresh, correctly signed issuer CRLs.
GlobalSign's authenticated certificate distribution points advertise HTTP; the verifier
upgrades those requests to HTTPS, restricts them to `crl.globalsign.com`, bounds response
sizes, and follows no redirects. Partial, indirect, delta, duplicate, and critical CRL
extensions are unsupported and fail closed. This restricts interoperability deliberately.

`dataset.bin` is generated by `just fido-mds-prep` and is ignored by Git. Its prepared format
contains the original signed BLOB and issuer CRLs rather than unsigned trusted rows.
Local `--source` files undergo the same verification as downloaded BLOBs; issuer CRLs still
require network access. Old unsigned assets must be regenerated. Expired embedded evidence
is skipped on startup, and the scheduler obtains a fresh verified BLOB before attestation
policy becomes available.

A runtime update atomically replaces withdrawn model/root associations. Lower BLOB numbers
are rejected. The same number can refresh CRLs only when its authenticated payload hash is
unchanged. Trust expires at the earliest BLOB `nextUpdate`, signing-certificate expiry, or
CRL `nextUpdate`, including before any cached attestation policy is used. The scheduler polls
daily and also refreshes before this deadline. Legacy DB rows have no verification deadline
and cannot authorize attestation until a verified refresh succeeds.

When attestation is optional, unavailable or expired metadata disables the opportunistic
attestation attempt and registration can continue as an ordinary passkey ceremony. Enforced
attestation continues to fail closed. An unverified legacy BLOB number cannot prevent the
first authentic refresh, even if the legacy number was greater.

Database-backend migration preserves the authenticated payload hash and verification deadline.
Sources without both verification columns receive empty/zero evidence and require an authentic
refresh before they can authorize attestation.
