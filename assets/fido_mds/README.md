# FIDO MDS signing trust

`root-r46.pem` is the self-signed GlobalSign Root R46 certificate designated by the
[FIDO Alliance metadata page](https://fidoalliance.org/metadata/) as the MDS BLOB signing
trust anchor. It was retrieved on 2026-10-12 from
[GlobalSign's certificate distribution](https://secure.globalsign.com/cacert/rootr46.crt).
The published PEM is also available on
[GlobalSign's root test page](https://valid.r46.roots.globalsign.com/).

SHA-256 over its DER encoding:
`4FA3126D8D3A11D1C4855A4F807CBAD6CF919D3A5A88B03BEA2C6372D93C40C9`.

The public CA root is insufficient by itself: the signing leaf must have the exact SAN
`mds.fidoalliance.org`, digital-signature usage, TLS server-authentication usage, and valid
non-CA constraints. The current official service uses RS256 with an `x5c` signing chain.
Noncritical JWS extensions such as `kid` are ignored. Unsupported critical extensions,
alternative algorithms, and header-directed certificate downloads are rejected. Supporting a future
signing profile or trust-root rotation requires a reviewed
code/asset update; trust anchors are never accepted from the downloaded BLOB.

Following the [MDS processing rules][mds-rules],
all non-root signing-chain certificates require fresh, correctly signed issuer CRLs.
GlobalSign's authenticated certificate distribution points advertise HTTP; the verifier
upgrades those requests to HTTPS, restricts them to `crl.globalsign.com`, bounds response
sizes, and allows at most five HTTPS redirects within the same origin. Partial, indirect, delta,
duplicate, and critical CRL
extensions are unsupported and fail closed. This restricts interoperability deliberately.

`dataset.bin` is generated by `just fido-mds-prep` and is ignored by Git. Its prepared format
contains the original signed BLOB and issuer CRLs rather than unsigned trusted rows.
Local `--source` files undergo the same verification as downloaded BLOBs; issuer CRLs still
require network access. Old unsigned assets must be regenerated.

The immutable asset shipped in a trusted release is verified at the latest signing-certificate
`notBefore` or bundled CRL `thisUpdate`. Signatures, chain constraints, revocation, and all evidence
validity intervals are checked at that time. This private startup path supports offline installs
long after the bundled CRLs expire. Public deserialization and online downloads still require
current certificate and CRL evidence; a downloaded timestamp cannot enable historical validation.
The embedded asset replaces legacy unverified rows or an older verified snapshot. It never replaces
a newer authenticated snapshot, including an expired or empty one containing model withdrawals.

A runtime update atomically replaces withdrawn model/root associations. Lower BLOB numbers are
rejected even when the stored evidence expires. The same number can refresh CRLs only when its
authenticated payload hash is unchanged. `nextUpdate` schedules refreshes, with seven days of
publication grace for newly ingested files. Evidence freshness uses certificate/CRL expiry.

Authenticated last-known-good rows remain usable for login and attestation registration during
outages or late publication. Staleness generates a rate-limited warning and prompts refresh;
it does not lock out users. This availability choice can delay learning of new device revocations.
Known withdrawn or compromised models remain rejected; legacy unsigned rows cannot authorize
attestation. Optional attestation can fall back when no verified snapshot is available.

The scheduler refreshes at least daily, or hourly when evidence needs renewal. Errors back off
exponentially from ten minutes to six hours. HTTP 429, Retry-After, and small HTTP 200 throttle
messages are honored. MDS redirects allow the same HTTPS origin or the reviewed
`mds.fidoalliance.org` / `mds3.fidoalliance.org` hosts; credentials, downgrades, and other origins
are rejected. Cache keys include snapshot version, hash, and evidence deadline, and replacement
clears the previous CA list.

Database-backend migration preserves the authenticated payload hash and verification deadline.
Sources without both verification columns receive empty/zero evidence and need an authentic
embedded seed or refresh before they can authorize attestation.
